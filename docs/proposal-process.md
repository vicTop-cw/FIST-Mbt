# 提案→定案→执行流程规范

> **为什么立这个规范**：2026-10-22 治理巡检发现，`reports/2026-10-16-future-plan.md` 是一份「后续计划」却放在了报告目录，内容也未整合进 `improvement-plan-20261010.md`——典型的 agent 乱象：计划散落、缺乏闭环、无人对账。本规范把「计划」纳入与「报告」「决策」同等的治理闭环，杜绝「写了就忘、写了就飘」。

---

## 0. 流程全景

```
 ┌─────────┐     ┌─────────┐     ┌─────────┐     ┌─────────┐     ┌─────────┐
 │  提案    │ ──→ │  评审    │ ──→ │  定案    │ ──→ │  执行    │ ──→ │  归档    │
 │Proposal  │     │ Review  │     │Decision │     │Execute  │     │Archive  │
 └─────────┘     └─────────┘     └─────────┘     └─────────┘     └─────────┘
  写方案+比选     六帽/技术评估   写入decision   按plan落地      移docs/archive/
  放proposals/   收集证据        记录定案结论    出report         提案失效时
```

与既有 `SOP.md` 的 7 阶段循环互补：**SOP 管「怎么干」，本规范管「干什么、干之前要什么手续」**。

---

## 1. 阶段 0.5 · 提案（Proposal）

### 1.1 什么需要提案

| 类型 | 必须走提案 | 不必提案 |
|---|---|---|
| 新功能/新方向 | ✅ 是 | — |
| 跨模块重构 | ✅ 是 | — |
| 架构决策（如辅助件放置、公开 API 新增） | ✅ 是 | — |
| 守卫族新增 | ✅ 是 | — |
| BUG 修复 | — | ❌ 否（走 `report_bug` → `bug_fix`） |
| 文档/格式/拼写 | — | ❌ 否（直接 commit） |
| 单文件重构 | — | ❌ 否 |

### 1.2 提案文件规范

- **目录**：`docs/proposals/YYYY-MM-DD-<主题>-proposal.md`
- **命名强制**：日期前缀 + `-proposal` 后缀，与报告（`-report`）、决策（`-decision`）同级
- **内容模板**：见 `docs/proposals/TEMPLATE.md`
- **必备章节**：
  1. 背景与问题（1-3 句，不铺垫）
  2. 方案对比表（至少两列：方案名 / 做法 / 改动量 / 适合）
  3. 推荐路径（必须显式选一条，不允许「都可以」）
  4. 四态对齐表（cl1-cl7）
  5. 待用户拍板的决策点（D1、D2…）
  6. 落地顺序（P0→P1→P2）

### 1.3 提案写入纪律

- **不许直接写 improvement-plan**：plan 是「已定案事项」的集合，未定案的先放 proposals/
- **proposals/ 不是草稿堆**：同一主题只保留最新一份提案，旧版移 `docs/archive/`
- **提案即占位**：proposals/ 里的文件 = 排队等定案的议题，指挥官每周审视一次

---

## 2. 阶段 0.6 · 评审（Review）

### 2.1 评审触发条件

- 提案写入 `proposals/` 后，指挥官决定是否启动评审
- 评审前必须完成：方案对比表 + 四态对齐表 + 至少一条实测证据（L3+）

### 2.2 评审形式

| 形式 | 适用 | 产出 |
|---|---|---|
| 六顶帽辩论 | 方向性决策（如架构选型） | `debate_verdict` 收敛率 + `reports/YYYY-MM-DD-<主题>-review.md` |
| 技术探针 | 可行性验证（如能否机械批处理） | 实测读数 + `reports/YYYY-MM-DD-<主题>-probe.md` |
| 快速评审 | 改动量 < 100 行、零架构影响 | 指挥官直接定案，跳过六帽 |

### 2.3 评审产出

- 评审报告写入 `reports/YYYY-MM-DD-<主题>-review.md`
- 提案更新：评审中发现的证伪点、新方案、量化数据追加进提案文件（提案文件是活文档，评审期间持续更新）

---

## 3. 阶段 0.7 · 定案（Decision）

### 3.1 定案文件规范

- **目录**：`docs/decisions/YYYY-MM-DD-<主题>-decision.md`
- **命名强制**：日期前缀 + `-decision` 后缀
- **必备章节**：
  1. 定案日期与定案人（用户 / 指挥官 / 副机联合）
  2. 最终选择（引用提案里的方案名，不重复写理由）
  3. 关键约束（「不许做什么」必须显式列出）
  4. 收口判据（用什么数字 / 测试 / 守卫认定完工）
  5. 遗留与豁免（没解决的问题、主动接受的债务）

### 3.2 定案写入纪律

- **一主题一份决策**：同一主题多次定案时，旧版移 `docs/archive/`，新版覆盖写入
- **决策即锁定**：决策写入后，proposals/ 里对应提案移 `docs/archive/`
- **决策引用**：后续执行报告、任务描述必须引用决策文件路径

### 3.3 决策点清单（从提案继承）

提案里的 D1、D2… 在定案时必须逐条关闭：
- ✅ 已选择：写明选了哪项
- ⏸️ 已豁免：写明豁免理由 + 债务归属
- ❌ 已推翻：写明推翻证据

---

## 4. 阶段 0.8 · 执行（Execute）

执行阶段与 `SOP.md` 的 7 阶段循环完全对齐，此处只补「定案后怎么接 SOP」的桥接规则：

### 4.1 桥接到 SOP 的步骤

1. **定案写入 decisions/** 后，把定案内容同步进 `improvement-plan-20261010.md`（或新建 improvement-plan）
2. **按 SOP §单轮节奏** 发布根任务到隔离命名空间
3. **任务描述必须引用决策路径**：`详见 docs/decisions/YYYY-MM-DD-<主题>-decision.md`
4. **每轮产出报告**：`reports/YYYY-MM-DD-<任务名>-report.md`

### 4.2 执行纪律

- **无决策不执行**：improvement-plan 里的每条必须能追溯到一份 decision 文件
- **执行即验证**：每完成一轮，用 `output_validate` 验 cl1-cl7
- **零回归**：`moon test --target js` 全量绿是提交硬门

---

## 5. 阶段 0.9 · 归档（Archive）

### 5.1 触发条件

- 执行完成 + 报告通过终审 + 归档任务 verify 通过
- 提案被主动废弃（方案被证伪、用户决定不做）

### 5.2 归档操作

```
mv docs/proposals/YYYY-MM-DD-<主题>-proposal.md docs/archive/
mv docs/decisions/YYYY-MM-DD-<主题>-decision.md docs/archive/   # 完工后保留，废弃时移走
```

### 5.3 归档目录结构

```
docs/archive/
  YYYY-MM-DD-<主题>-proposal.md     # 已定案/已废弃的提案
  YYYY-MM-DD-<主题>-decision.md     # 已废弃的决策（完工的保留）
  YYYY-MM-DD-<主题>-review.md       # 评审报告（可选归档）
```

## 6. 与既有规范的关系

| 文件 | 管什么 | 本规范不覆盖 |
|---|---|---|
| `SOP.md` | 单轮执行节奏（发布→认领→执行→验收→归档） | ✅ 不重复 |
| `DOCS-STRUCTURE.md` | 文档命名与放置规则 | ✅ 只引用，不重写 |
| `AI-DEVELOPMENT-STANDARD.md` | 开发规范（r1-r5, f1-f5） | ✅ 只引用，不重写 |
| 本规范 | 提案→定案→执行闭环 | 🆕 新增 |

---

## 7. 违规与债务

| 行为 | 定性 | 处理 |
|---|---|---|
| 计划写在 reports/ 而非 proposals/ | 违规 | 立即移入 proposals/ 并补写提案头 |
| improvement-plan 条目无对应 decision 文件 | 债务 | 暂停执行，先补决策 |
| 提案写入后超过 7 天未评审 | 挂起 | 指挥官主动审视，要么启动评审要么归档废弃 |
| 评审通过但未写 decision 文件即开工 | 违规 | 立即停工，补写决策 |

---

## 8. 一句总结

**计划不是报告，报告不是决策，决策不是执行——四件事各有各的文件、各有各的纪律。本规范把它们焊成闭环：proposals/ 排队 → review 评审 → decisions/ 锁定 → SOP 执行 → archive/ 归档。任何一环断裂，下一环不许启动。**
