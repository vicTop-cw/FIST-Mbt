# 设计文档：冲榜概率门禁 + 调研库 + 方法论固化

> 日期：2026-09-24 · 状态：待实施 · 面向：2026 MoonBit 黑客松（9 月赛 + 季度评选）
> 目标：**一等级 ≥60% / 二等级 ≥80% / 三等级 ≥95%** 获奖概率，以「4-AI 自评分门禁」验证；不过即自我迭代，直至全过。

---

## 一、背景与目标

fist-mbt（纯 MoonBit 的 MCP Server + 任务编排 + 自进化底座）目标进入赛事前 10 并冲刺更高名次。
工程底子已硬：61 MCP 工具 / 148 测试 / JS+Native 双端全绿 / CI 三轨道绿 / 自驱闭环可自我迭代。

本设计把两类动作一起固化：
1. **调研库 + 方法论**：凡与目标项目相关功能都应先调研再迭代（QClaw 两份调研报告 + 自研 selffit 调研）。
2. **概率自评分门禁**：用 **4 个 AI 顺序打分、全档达标** 来客观确认「获奖概率是否达到目标」，不达标即触发下一轮自我迭代。

## 二、概率如何确认（门禁机制）

### 2.1 目标概率
| 档位 | 目标 |
|---|---|
| 一等级 | **≥ 60%** |
| 二等级 | **≥ 80%** |
| 三等级 | **≥ 95%** |

### 2.2 4 个评分 AI（顺序固定，全部必须通过）
| # | AI | 载体 |
|---|---|---|
| AI1 | 你自身 | 当前会话 agent |
| AI2 | atomcode CLI · LongCat | `atomcode -p "<prompt>"`（headless） |
| AI3 | codearts CLI · 盘古 | `codearts ... -p "<prompt>"` |
| AI4 | atomcode CLI · kimi k3 | `atomcode -p "<prompt>"` |

- 每个 AI 用**统一 rubric 提示词 + 同一证据快照**，输出 `JSON：{p1, p2, p3, verdict}`。
- **打分口径 = 全档达标**：任一 AI 的 `p1≥60 && p2≥80 && p3≥95` 不成立，则该 AI **不通过**。
- **聚合 = AND**：只有 **全部 4 个 AI 全档达标**，本轮门禁 `PASS=是`。

### 2.3 评分标准（比严苛型稍宽一档）
沿用加权评估表，评估口径「稍宽」= 只要「证据 + 合理外推」即可给分（严苛需「确凿对标 + 高置信证据」）：

| 维度 | 权重 | 满分 |
|---|---|---|
| 完成度 | 25% | 25 |
| 技术难度 | 20% | 20 |
| 创意 / 生态价值 | 30% | 30 |
| 美观 / 演示可复现 | 25% | 25 |

由 4 项得分 → 换算为三档获奖概率 `p1/p2/p3`，逐档与目标比较。

### 2.4 迭代循环（不过就继续）
```
评估快照(memory/research/recent-market.md + index.md + BACKLOG.md + 提交/cI 状态)
   → 4-AI 顺序打分（全档达标才过，任一不达即 PASS=否）
        → PASS=是 → 记录 score-YYYYMMDD.md，达标
        → PASS=否 → 从 BACKLOG.md / P0-P3 取下一批写入审视报告 Next Tasks
                      → 走自驱闭环(publish→拆→执行→验收) → 重新评估 → 回到打分
（循环直至全部 4 个 AI 全档达标）
```

### 2.5 证据底座（喂给每个 AI 的事实快照）
- `memory/research/recent-market.md`：**近 3 个月** mooncakes/行业新增项目、同类竞品（MCP server / agent 编排）、赛事评审偏好、fist-mbt 现实 vs 竞品差距。
- `memory/research/future-roadmap.md`：fist-mbt **未来可扩展清单**（P0-P3 待办、五方向可移植机制、生态集成项）。
- `BACKLOG.md` + `git log` + CI 三轨道结论。

## 六、落地资产
- `scripts/score_gate.py`：顺序拉起 4 CLI（headless）、注入 rubric+证据、解析各 verdict、AND 汇总，输出 `AI1..AI4 得分表 + 结论`；**任一步无法如实执行则如实上报、不伪造通过**（金条八 / 失败即暴露）。
- `scripts/_ai_prompt.md`：统一 rubric 提示词（维度、稍宽口径、输出 JSON 契约、禁止自吹）。
- `memory/research/score-YYYYMMDD.md`：首次实跑的多头打分结果。

## 七、非目标与风险
- **非目标**：本轮不新增/改动任何 MCP 工具，不改既有工具语义；评分脚本仅作门禁判据，不嵌入产品运行时。
- **风险**：codearts/atomcode 的模型在线态、auth、headless 输出格式差异——实施时对 4 个 CLI 逐个 dry-run；不可如实驱动者如实报告，不降级为「视为通过」。
- **诚实铁律**：概率是「自评快照」，非客观保证；以留痕的多头打分为依据，不夸大。

## 七·A、质量标准（主次分明，写死进每次迭代/门禁）

> 这些是贯穿一切工作的**硬性标准**，不只针对本设计。区分主/次，主为先决硬门槛、次为须尽力保持的工程纪律；冲突时先保「主」。

**主 · 阻断性硬门槛（不达标即打回重迭代，门禁不通过）**
1. **无硬编码**：源码/脚本/测试无盘符、`/home`、`/Users` 等绝对路径；路径相对或参数化（环境变量/参数注入）。
2. **无任何回归**：既有行为与 148 项测试语义不变；改动不破坏既有功能。
3. **测试全绿**：`moon test --target js` 与 `--target native`（Windows 用 `-j 1`）双端全绿。
4. **功能兼容**：不改变既有 MCP 工具的参数/返回/语义（新增可，破坏不可）。
5. **任意机器结果可完全复现**：干净机器上 `moon update && moon run/test` 即得同等结果；不依赖本机私有路径/我个人会话状态。

**次 · 期望性工程纪律（优先满足，非阻断但失分项）**
6. **文档即实现**：文档与实际行为一致；改实现必同步文档、反之亦然（含本计划涉及的 README/USAGE/AGENTS/模板/调研库）。
7. **主次的落点**：当「功能增量」与「标准」冲突时，以主标准为准——宁可在功能上让步，不牺牲可复现与兼容。

**落地**：上述 1–5 作为**每个子任务回传与每次门禁的硬验收**；6 作为文本检查项。写入 `docs/polish-plan.md` §四验收标准，替代/升级其中对 135 的过时引用为「当前双端全绿数」。

## 八、验收标准（每次门禁/迭代必过）
1. 4 个 AI 均如实完成一次打分且全档达标 才记 `PASS=是`。
2. 留痕完整：`score-*.md` + 证据快照 + 对应迭代的 commits/CI 绿。
3. 无硬编码（脚本路径相对/参数化）；无回归（`moon test` 不受影响）。
4. 文档即实现：BACKLOG/index/score 引用真实路径与状态。
