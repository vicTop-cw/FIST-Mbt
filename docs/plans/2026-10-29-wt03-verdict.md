## 分析：为什么「多一份 shell」是负债

**提案里没有的，主轨都做了** —— 这些恰恰是 shell 双轨最难做对的部分：

| 主轨已有的能力 | 在 shell 里重做要多少代价 |
|---|---|
| `--sparse` 探测 + 只在「不认识这面旗」时回退 | 两个脚本各写一遍，且 bash/pwsh 判错方式不同 |
| manifest 记账（`wt-<task>.json`）| 要自己管 JSON 读写，pwsh 与 bash 各一套 |
| `rc` 契约（0/1/2/4）| 三轨要保证同一个退出码含义 |
| 21 格自检 | 双轨各要写一遍等价测试 |

**⇒ 三份同名逻辑（bash + pwsh + python）的维护成本不是 3×，是 3× + 不一致风险。**
本仓 `check_two_faces.py` 抓的正是这个形态：**同一规则多份实现，改一处忘两处 = 两个行为不一致。**
而 WT-03 会直接制造**三份**。

**关键事实（反驳「无 python 环境」这个理由）**：
- **CI 三条 workflow 全部用 python**（`attest.yml`/`ci.yml`/`fist-ci.yml`）
- `scripts/` 下 **10 个 `.ps1`** 没有一个是「同名能力的第二实现」——都是**平台专属**动作
- **`bin/` 在仓内无任何先例** ⇒ 提案会新开一个目录约定，只为放 4 个重复实现

**⇒ 「python 轨够用」成立。唯一的 shell 场景是「连 python 都没有的机器」——
而那种机器上，本仓其他 100+ 个 `scripts/*.py` 也都跑不了。**
