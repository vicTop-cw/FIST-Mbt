# FIST-Mbt

Use this skill to work with the FIST-Mbt codebase — a pure MoonBit implementation of the FIST commander task allocation system, exposed as an **MCP server with 129 tools (真源=src/server/server.mbt；守卫 scripts/check_tools_sync.py) + 3 resources + 2 prompts**, plus self-driving (selfdrive) loops, Omega strong verification, and an ecosystem of meta-prompt modes.

## Default workflow

1. Identify the user's intent: understanding FIST concepts, running a self-driving session, debugging, adding features, or extending MCP tools.
2. Load the relevant reference from `references/` per the routing table below.
3. For code changes, verify with `moon check` / `moon test` before completing; `moon fmt` + `moon info` before handoff.
4. For MCP tool questions, prefer a live `tools/list` over docs (docs may lag; see `references/mcp-tools.md`).
5. **Run the server with Node >= 24**, and run `python scripts/patch_esm_main.py` (idempotent) before starting `node cmd/cli/cli.js` directly — ESM output needs a require shim.

## Project overview

- **Seven-state task state machine**: 待领取 → 已领取 → 拆分中 → 执行中 → 待验收 → 已完成 → 已归档, plus 已打回 / 已暂停 / (reopen paths)
- **Hierarchical decomposition**: `T0 → T0.1 → T0.1.2`, K-value depth (root=3, decrement, ≤1 = atomic leaf)
- **DAG extensions**: critical path, slack (PERT/CPM), schedule with load-aware assignment, Monte Carlo completion forecast, cost routing
- **Self-driving loop** (`selfdrive_*`): `selfdrive_init/_get/_append/_review_tick/_review_ready/_publish_next/_pick_next/...` — review-report-driven continuous iteration
- **Omega strong verification** (opt-in, per task tree): `task_plan_deep(omega_strong_verify=true)` → every leaf carries `omega:required` → `omega_spec_create` → `omega_spec_review` → execute → `omega_result_verify` → `verify`; bounce limit 3 (max 10), auto-escalate to human
- **Laya decision routing**: `laya_decide` probes a local Laya sidecar for difficulty/domain/sensitivity; auto-degrades (`available:false`) — note BUG-14: the `decision` field is missing on 3 of 4 return paths (unfixed), rely on degradation + record your own reasoning
- **Marketplace/executor routing, GitHub sync channel (8 tools)**, **memory/evolve self-memory**, **cost/progress gates**, **board/health observability**
- **Multi-tenant namespaces**: always isolate automated runs in their own namespace; never touch `default` or other agents' namespaces

## Gotchas (hard-earned, keep in mind)

- **Claim before execute** — the state machine rejects unclaimed `plan`/`execute`.
- After all leaves are green the parent **auto-rolls to 待验收**; verify it directly, do NOT re-claim (illegal transition).
- `retry` lands in 执行中 where `execute` refuses (BUG-2, unfixed): detour `pause → resume → execute` (tool name is `resume`).
- **Timestamps are stamped server-side** — no tool takes a `now` argument (BUG-33 policy). `call_log` and ledger times are server-clock values, so a caller cannot forge them.
- **Paths must be relative** for bug-family tools (`report_bug`/`bug_list`/`issue_scan`); they resolve against the **server process cwd** — and `memory`-family tools do NOT validate (BUG-5 contract split, unfixed). Probe the landing spot once per session.
- `report_bug(publish_task=true)` drops the fix root task into namespace `"bugs"`, detached from your tree (BUG-8), and `list` may not show it (BUG-12) — reconcile via `get(task_id)`.
- There is **no bug_close API** (BUG-9): bugs stay OPEN even when fix tasks complete — reconcile manually via `bug_list` + task states.
- `issue_scan` matches literals on raw lines: it hits comments and its own rule table (BUG-15, measured 0/8 high precision). Treat findings as candidates; verify by reading context before `report_bug`.
- `status_summary`/`project_health`/`fist://overview` may report a stale version (BUG-16): trust `moon.mod`.
- Windows native target has a rare heap corruption under parallel test (`-j 1` mitigates); **JS backend (Node ≥ 24) is the authoritative gate**.
- ESM: run `python scripts/patch_esm_main.py` before `node main.js`; JS backend also ships `scripts/fist.py` (Python driver) — often the simplest route.

## Self-driving modes (meta-prompts, see the meta-prompt library)

Seven modes, identifiers exactly as `mode_list` returns them: 推进 `advance` / 打磨 `polish` / 验证 `verify` / 寻虫 `bugfind` / 修复与合并 `fix_and_merge` / 清整 `tidy` / 探索 `explore` — each with a meta-prompt template at `templates/pipeline_mode_<identifier>.md` (precheck with `mode_templates`). Six of them are workers; `explore` scores goal complexity 0..5, picks one worker, and may run several workers in parallel only when their declared file scopes are pairwise disjoint (`reserve_scope` + `conflicts_check`). Loop pattern: progress ledger + one closed loop per segment; failures skip forward, never stall.
