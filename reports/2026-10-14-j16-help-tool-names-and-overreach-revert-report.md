## ① J16 判据（补 J14 的数字和盲区）

**缺口**：`cmd/cli/help_topics.mbt` 的 `fist help tools` 分组表是**手写清单**，
而 **J14 只判「分组数字之和」与「组数」**：
把 `publish` 写成 `publsh`、漏列一个、或多列一个不存在名时，**数字和仍然对**，J14 全绿 ⇒ 漂移看不见。

**为什么不能"改真源生成"**（连续三轮建议的落地形态）：分组**归类**（哪个工具属哪组）是人工知识，
真源只给工具名集合。故取等价目标：**判据化一致性**。

**J16 实现**（`check_doc_surface.py`，与 J14 同族）：
解析 `"  [Group N] name1 name2 …` 行的工具名串，与 `_tool_registry.real_tools()` 对表：
- 真源有而表里没有（漏列/拼错）⇒ 红并点名
- 表里有而真源没有（多列/拼错/已退役）⇒ 红
- 任一侧为空集 ⇒ **FATAL 自拒**（判据饿死不等于没问题）

**变异实测 3/3**：
```
[1] publish → publsh        ⇒ J16 报"漏列/拼错 1 个真源工具：publish"
[2] 删 supervisor_status    ⇒ J16 报"漏列/拼错 1 个真源工具：supervisor_status"
[3] 插 bogus_tool_xyz       ⇒ J16 报"出现 1 个非真源工具名：bogus_tool_xyz"
还原后 rc=0
```

**顺带：J10 立刻生效**。J16 一落地，J10「判据范围自述==实现」立即抓出三处 J 系列自述滞后
（`AGENTS.md` / `AI-DEVELOPMENT-STANDARD.md` / `templates/pipeline_mode_tidy.md` 都还写 J1-J15）
—— 这是 J10 按设计工作的实证（新判据落地会立刻暴露"自述范围没跟上"）。

## ② 越界改动的自查与回退（本轮最重要的诚实记录）

### 症状
`78e02f0` 提交后，`templates/pipeline_mode_tidy.md` 显示 **20+9 行**变化，而我只改了一处 J 系列自述。
diff 里出现 `+eject /`、`+etry /`、`+ead；` 等**首字母丢失**的残迹。

### 取证（两层，必须分清）
1. **`78e02f0^` 原版就已含 23 个控制字符**：CR×11 / TAB×2 / BS×3 / ESC×6 / VT×1
   ⇒ 丢失的字母恰是**转义首字母**（`\t`→TAB 吃 `t`、`\r`→CR 吃 `r`、`\b`→BS 吃 `b`、
   `\e`→ESC 吃 `e`、`\v`→VT 吃 `v`）
   ⇒ 该文件**早已被一次转义序列解释破坏**（`task_plan_deep`→`ask_plan_deep`、`reject`→`eject`），
   **不是本轮引入的**。
2. **但我的脚本确实改变了它**：Python 文本模式读写把 11 个裸 CR 规范化成 LF
   ⇒ 相对原版多出排版变化。这是**超出我本意的副作用**，且提交时未察觉。

### 处置
- 取 `78e02f0^` 的**原始字节**，只重新应用我本意的那一处（J1-J15→J1-J16），**二进制写回**
  （保留 CR 等原始字节，不做换行转换）
- 复核：相对 `78e02f0^` 的净差异 = **0 行**（我的 J1-J16 改动生效 + CR 保留原样）
- 该文件 CR 计数恢复为 **11**（与原版一致）

### 为什么没顺手修那 23 个控制字符
那是该文件的**作者排版/内容问题**，且需判断"哪些是原意"（例如 `\t` 到底该是 `task_plan_deep`
还是别的词）——**越权判断风险高**。本轮曾一度尝试"顺手全修"（写了词表修复脚本，
把 `eject`→`reject` 等按真源工具名补回），**中途判定这属改他人文件排版，已回退**。
只把预存在缺陷如实记录，交作者/owner 决定。

**教训（可复用）**：**用 Python 文本模式读写他人文件会静默改变其字节形态**（CRLF/CR/控制字符）。
改这类文件应：① 先 `git show <rev>:<path>` 取原始字节；② 只做目标替换；③ 二进制写回；
④ 提交前 `git diff --numstat` 核对变更行数与预期一致。
