## 三、分析：为什么撤回接线（本单最重要的一条）

### 3.1 「修好了一半」

| 层 | 修好了吗 |
|---|---|
| **依赖层**：`dispose()` 能真的 close 了 | ✅ **修好了**（P2: 150s → 5.06s）|
| **调用层**：有没有人调 `dispose()` | ❌ **没有** —— `commissar_watch` **只 subscribe、不保存句柄** |

```moonbit
// src/ops/ops_commissar.mbt:191-235
let source = @rhop.from_filesystem_with(events, ..., true)
let _ = source.subscribe(@rx.Observer::new(...))   // ← 返回值被 `let _ =` 丢弃
eprintln("commissar watch started: ...")
}
```
**⇒ 补丁只让「dispose 时」能 close，而这个函数根本不 dispose。**
一旦注册成 MCP 工具，**server 依然永不退出**。

### 3.2 判例：三层塔（与判例-29 同族的第三层）

```
依赖实现了能力（依赖格）              ← 本单已修 ✅
  → 调用方有能力调用（机制格）        ← 有能力（函数存在）
    → 调用方真的调了（实现路径格）    ← ❌ 卡在这一层（从不 dispose）
```
**判例-29 的老坑换了第三层外壳又出现了一次。**

### 3.3 更根本的问题：MCP 与「持续订阅」不匹配

**MCP 是请求/响应模型。** 任何「长驻句柄」都会让**进程生命周期与工具调用耦合**。

**⇒ 建议不是「让订阅可关闭」，而是改成短轮询**：
```moonbit
commissar_poll(since_seq)   // 无状态、无句柄、进程随时能退出
```
**这与 MCP 的请求/响应模型天然匹配。**

### 3.4 另一点：`commissar_watch` 不是同步阻塞，这反而更危险

它**注册回调后立即返回**（函数里没有 `while`/`loop`/`sleep`），
靠 `fs.watch(persistent:true)` 让事件循环保持活跃。

**⇒ 表现是「活着、能响应，但永不退出」** —— 比「阻塞」更难发现（阻塞至少看得出来）。
