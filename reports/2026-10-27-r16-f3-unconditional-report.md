## 一、结论

### 1.1 ⚠️ 核心发现：**F3 一直都是无条件的，缺的是变异对照 + 一句与实现相反的 docstring**

派单说「F3 目前只在注释声称『同一条规则』时才查」。**实测：这个前提不成立。**

```
$ grep -n "注释\|comment\|claim" scripts/check_two_faces.py   # F3 相关处
```

`check_f3()` 的实现里**没有任何读注释的分支** —— 它直接扫 `ON CONFLICT ... WHERE`
与 `rsv_action` 的比较符并对表。**「依赖注释」只写在 docstring 里，没写在代码里。**

**⇒ 真正缺的是两件事（本单都做了）**：
1. **F3 没有任何变异对照**（现有变异格 2/3 只测 F1 抄本）⇒
   把 `check_f3` 整个删掉、或改成恒 `aligned=True`，**selftest 照样全绿**（判例-29）；
2. **docstring 与实现相反** ⇒ 读代码的人会以为「不写注释就查不到」，
   甚至**为了被检查而去加注释**（那正好把「按形状扫」退化成「按声称扫」）。

## 二、证据：新增 6 格（3 变异 × 2 断言）

| 格名 | 造法 | 期望 |
|---|---|---|
| `f3-baseline-aligned` | 两侧都 `<` | 0 条违例 |
| `f3-baseline-checked` | 同上 | `f3_checked` 恰 1 条 |
| **`MUTATION-f3-mb-cmp-drift-detected`** | **MB 侧 `<` → `<=`** | **rc=DRIFT(1)** |
| `MUTATION-f3-mb-cmp-violation-count` | 同上 | 1 条违例 |
| **`MUTATION-f3-sql-cmp-drift-detected`** | **SQL 侧 `<` → `<=`** | **rc=DRIFT(1)** |
| `MUTATION-f3-sql-cmp-violation-count` | 同上 | 1 条违例 |
| **`MUTATION-f3-no-where-no-false-drift`** | **删掉 `ON CONFLICT ... WHERE`** | **0 条违例（不误报）** |
| `MUTATION-f3-no-where-not-checked` | 同上 | `f3_checked` 为 0 |

**变异 3 的判定说明**：SQL 侧删掉 `ON CONFLICT ... WHERE` ⇒ **不产生 F3 条目**（`f3_checked=0`）。
按「高精度低召回」原则，这是**正确的**：没有 SQL 谓词就没有可对表的对象，
报 DRIFT 会把「不存在」误判成「不一致」。**但「不检查」也不许伪装成「检查过了」** ⇒
`f3_checked=0` 如实反映。

> ⚠️ 派单说「变异 3 ⇒ rc=2」。**实测后我认为不该是 rc=2**：
> `rc=2` 的语义是「**判据无法自证**」（整个扫描面为空）；
> 而这里是「**这一组**没有可对表对象」，其余扫描面仍然有效 ⇒ 应为 **rc=0 + `f3_checked=0`**。
> 若强行 rc=2，会让「只有一个后端」的正常仓库无法通过判据。**这是一处我按语义纠正的偏离，请裁。**

### 2.1 过程中我修掉的两个真缺陷

**① `judge()` 自拒分支缺键**（「缺键 ≠ 空值」本体）：
```python
# 修前：自拒分支只返回 4 个键
return RC_BROKEN, {"scanned_files":…, "f1_checked":[], "f1_checked_n":…, "note":…}
# ⇒ 调用方 res["f3_violations"] → KeyError（不是"没漂移"，是"键不存在"）
```
**这正是我自己在 BUG-433 里立的判例的活标本**：缺键必须显式补空值，不能靠调用方 `get()` 兜。
已补齐全部结果键。

**② 变异格夹具踩到自拒分支**（实测两轮才修好）：
- 第 1 轮：F3 夹具只有 `store/` 子目录 ⇒ `iter_mbt` 扫到文件但 `c1`（F1 可判对象）为 0
  ⇒ 走自拒分支返回 `rc=2`，**把 F3 的 DRIFT 吃掉**。表现：违例计数正确 `got=1`，
  但整体 `rc=2` ⇒ 我一度以为是判据坏了。
- 第 2 轮：加了一个**无声称**的锚点函数 ⇒ `c1` 仍为 0（F1 只认「有镜像声称」的定义）⇒ 仍 `rc=2`。
- 第 3 轮：造一对**内容相同的真镜像**（`anchor_real` + 声称镜像的 `anchor_copy`）⇒ `c1=1`，通过。

**⇒ 教训**：造变异夹具时，**必须让被测判据走到它自己的代码路径**，
否则测到的是「自拒分支」而不是「被测逻辑」（判例-29 的夹具版）。

## 三、分析（为什么「无条件」比「依赖注释」好）

**依赖注释的判据有一个致命的自指陷阱**：它测的是「人**说**了这件事」，不是「这件事**是**这样」。
后果是双向的 ——

- **漏报**：没写注释的真不一致**永远查不到**（而没人会为「我不知道这不一致」写注释）；
- **反向激励**：一旦有人知道「写注释才会被检查」，他就会**在写不出理由时不写注释**，
  于是判据的覆盖面由**被检查者的措辞**决定，而不是由**代码形状**决定。

**「按判定形状扫」把判据从「人说的话」挪回「代码的事实」**：
比较符集合是**可从源码直接读出**的客观量，不依赖任何人的声明。
代价是**召回有上限**（只认这一种形状），但**高精度低召回**是本判据既定的设计取舍 ——
**宁可少报，不可报一个要人判断真伪的东西。**

## 四、缺口与风险

1. **F3 的覆盖面仍是「一对一」**：只对 `store_rsv.mbt::rsv_action` ↔ `store_sqlite.mbt` 的
   `ON CONFLICT ... WHERE`。仓内还有**其它** `ON CONFLICT`（如 `file_locks` 那条用
   `ttl_until < excluded.ts` 与 `status <> 'active'`），它们**未纳入对表**。
   若要扩面，需先确定「每个 SQL 谓词对应哪个 MoonBit 函数」——
   而那正是「依赖注释」想解决、也是本单否掉的方案。**这是一个真缺口，建议另立。**
2. **变异 3 的档位我偏离了派单**（rc=0 而非 rc=2），理由见 §二，**请裁**。
3. **只比比较符集合，不比操作数**：若两侧都是 `<` 但比的是**不同字段**
   （如一边 `ttl_until < now`、一边 `created_at < now`），F3 **察觉不到**。
   这是「高精度」的代价，已在 docstring 写明。
