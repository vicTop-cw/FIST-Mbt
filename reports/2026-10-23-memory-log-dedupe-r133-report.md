# R133 报告：每日日志整块重复常驻判据 + 无损去重（memory/2026-10-22.md 91MB → 250KB）

## 一、结果摘要

- **发现**：`memory/2026-10-22.md` 在 HEAD 上是 **91,871,620 字节 / 25,770 个 `## ` 块 / 仅 56 个唯一块**（最大单块重复 3,465 次；`memory/2026-10-21.md` 另有 9 次整块重复，320 块 / 102 唯一）。这不是排版问题：任何「取最后一次出现」的读法会读到旧状态，任何按块检索都会把同一结论读 N 遍；而它每轮随提交继续放大（历史 blob 5.2→6→12→18→30→60→91MB），把仓库本身拖成不可 clone 的形状。
- **根因定位**：`memory_consolidate`（`src/server/memory.mbt`，thinking 类 append-only）只追加**新内容**，不会重写旧块；`memory_gc` 只按字符数截尾归档。91MB 的重复块是**代理/合并行为**（整文件被自我追加/覆盖式合并）造成的，与工具实现无关——因此修在**仓内判据面**而不是改工具语义。
- **修复**：新增常驻判据 `scripts/check_memory_log_dedupe.py`（D1 整块重复必红 / D2 复制放大比必红 / D3 单文件体积上限必红；`--fix` 无损去重，写前复验唯一块集合不变），接线 `scripts/run_guards.py` 电池两格 + `scripts/README.md` 条目与 `BATTERY-REGISTRATION` 锚点；工作树内对两份日志执行 `--fix`。
- **读数**：`2026-10-22.md` 91,871,620 → 250,157 字节（25,770 → 56 块）；`2026-10-21.md` 1,209,035 → 340,635 字节（320 → 102 块）。对 HEAD 逐块哈希比对：唯一块集合 **56/56 与 102/102 完全一致，only_old=0 / only_new=0**（无损，没有删掉任何一条独有内容）。
- **常驻面**：裸跑 0 违例；`--selftest` 8 格全绿；电池 68 格 / 失败 0 / SKIP 5 / 缺执行面 0。

## 三、分析

1. **为什么修在判据面而不是改 `memory_consolidate`**：工具只做 append-only 追加，没有「同一结论写两遍」的路径；91MB 的形状是整文件被反复自我追加（每块内容逐字节相同，含时间戳）。这是**调用侧/合并行为**，把去重逻辑塞进工具会让 `memory_consolidate` 承担它看不见的全局上下文（跨进程、跨日文件）。判据面保持职责单一：文件坏了就红，`--fix` 只做可证明无损的机械去重。
2. **为什么按 `## ` 块而不是按行去重**：日志的语义单位是块；按行去重会把代码块/列表里的重复行删掉（信息破坏），且无法做「唯一块集合不变」这种强不变量。
3. **为什么阈值定在 15% / 2MB**：D1 对任何重复即红（整块重复没有合法场景）；D2 只在重复占比 >15% 时红，用于抓「每块复制两遍」之外的低比例放大；D3 对 >2MB 的单文件红——现有最大单日合法文件 340KB，2MB 留了 6 倍余量，避免正常长日志误红（本次 91MB 正是被 D3 与 D1 同时抓住）。
4. **首版缺陷与修法**：`dedupe_file` 起初「先写盘、后验证」，且在原文无尾换行时会补一个 `\n`，导致 `2026-09-24.md` 最后一块哈希改变、被复验拦下（rc=4）并已改动该文件一行；随后 `git checkout --` 还原、删掉补换行逻辑、把复验移到写盘之前、无重复时不写盘。当前实现满足「无重复 ⇒ 一个字节都不动」。

## 七、遗留风险

1. **并发追加竞态**：`--fix` 是读-改-写，若主机代理恰在同一秒追加，可能丢一次追加。当前无锁；建议后续把 `--fix` 纳入提交前钩子（单进程持有）或加 `.lock` 文件。
2. **重复来源未定位到具体调用方**：只证明不是 `memory_consolidate`。若同一放大再次出现，D1 会立刻红，但「谁写的」仍需现场抓（可对比 blob 增长与提交时间）。
3. **判据只扫 `memory/` 根下每日日志**：`reports/` 等其它 append-only 面若出现同类放大不在本尺覆盖内（当前无此迹象）。
4. **R132 及更早的未合分支**（R126/R127/R128+R129/R130/R131/R132）仍在远端待合，本单叠在 R132 tip 上；若主线先合其它单，需按常规 rebase。
5. 首跑电池两红已修（锚点同步），但 `BATTERY-REGISTRATION` 仍是手抄数——下一次加尺/加格仍会红，这是判据设计（同批改数），不是缺陷。
