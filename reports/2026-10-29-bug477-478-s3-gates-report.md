## 二、证据

### 2.1 BUG-477：改用带消费的门

**病灶**（`engine_rsv.mbt`）：`rsv_try_set` / `locks_try_acquire` 调 `judged_role_gated`，
它**只验签、不消费** ⇒ 同一张票可**无限重放**。

```diff
- let (role, role_source) = judged_role_gated(self, agent, challenge_nonce, challenge_sig~)
+ let (role, role_source) = judged_role_with_nonce(self, agent, challenge_nonce, challenge_sig~)
```
改**两处**（`rsv_try_set` / `locks_try_acquire`）。
`rsv_set`（第三处）**不改** —— 它没有 challenge 参数面，工具面零调用。

**关键约束（派单警告的）**：`judged_role_gated` 被 **5 处**消费
（含只读的 `challenge_pending_count`）⇒ **绝不能把消费塞进门函数**。
本单的做法是**只在两个消费者换函数**，门函数一行不动。

### 2.2 BUG-478：**同族是 7 个，不是 2 个**

派单说「`reserve_scope` / `lock_acquire` 不接受 namespace」。
普查实测（脚本 `temp/audit/lane_df_ns.py`，按工具块边界扫）：

| 工具 | 修前 ns | 修前路由 |
|---|---|---|
| `reserve_scope` | ❌ | ❌ |
| **`reserve_check`** | ❌ | ❌ |
| **`reserve_release`** | ❌ | ❌ |
| `lock_acquire` | ❌ | ❌ |
| **`lock_renew`** | ❌ | ❌ |
| **`lock_release`** | ❌ | ❌ |
| **`lock_status`** | ❌ | ❌ |

**⇒ 七个全缺。** 根因：这七个工具用的都是 `server.mbt:27` 的**进程级全局 `engine`**
（`make_engine()`，主库），**整个工具面不走多租户路由**。

**修法**（七个都改）：
```moonbit
"namespace": string_prop("可选：目标命名空间（默认 default；传入已 open 的 ns 时路由到该独立库）"),
...
let ns = get_str(args, "namespace", default="default")
let engine = match engine_for_ns(ns) {
  Ok(e) => e
  Err(m) => return Err(m)
}
```

**零回归论证**：`engine_for_ns("default")` ⇒ `engine_route_in` 的第①条出口返回**主引擎**
—— 与修前那个全局 `engine` 是**同一个实例**。⇒ 不传 `namespace` 行为逐字不变。

### 2.3 nonce 跨工具语义：**全局一次性**

```moonbit
// engine_rsv.mbt:535
pub fn s3_consume_nonce(agent : String, nonce : String) -> Bool {
  let k = agent_fp_of(agent)
  match s3_pending_nonces.get(k) {          // ← 按 **agent** 索引
    Some(arr) => { ... 找到即 arr.remove(found) ... }   // ← **移除**
  }
}
```
**⇒ 不是「每工具一次」，是「每 agent 一次」。**
`reserve_scope` 消费后，`lock_acquire` 再用同一张票 ⇒ `challenge_replayed`。
**这与派单倾向的一致，且代码本来就该这样**（`claim` 也是同一语义）。

### 2.4 三格锁 + 两个变异

| 锁 | 断言 |
|---|---|
| **`df_01`** | ★ 走**真实引擎函数** `rsv_try_set`：首次 `challenge_verified` ⇒ **同票第二次 `challenge_replayed`** |
| **`df_02`** | `judged_role_gated` **连调两次都是 verified** ⇒ 钉住「门函数不消费」，防有人把消费塞进去毒害 5 处只读消费者 |
| **`df_03`** | 七个工具 schema 都有 `namespace` **且** handler 都调 `engine_for_ns` |

**变异实测（都真跑）**：

| 变异 | 结果 |
|---|---|
| **M1** `rsv_try_set` 退回 `judged_role_gated` | **348/350**，**`df_01` 精确打红** |
| **M2** 删掉一处 ns 路由 | **349/350**，**`df_03` 精确打红** |

### 2.5 ★ 变异实测抓出我自己锁的缺陷（值得记）

**第一版 `df_01` 直接调 `judged_role_with_nonce`，没走 `rsv_try_set`。**
做 M1 时结果：**`df_01` 照样绿**，红的只有别处的形态计数锁。

**⇒ 那是判例-29 的老坑，我踩了第二次**：
**测了「门函数会消费」≠ 测了「消费者接的是会消费的门」。**
修法：`df_01` 改成**真调 `rsv_try_set` 两次**，用回执 `action` 里的
`challenge_verified` / `challenge_replayed` 判定。改完后 M1 精确打红。

**⇒ 「先跑变异再宣布完成」这条纪律本单第二次救了我。**

## 三、分析

### 3.1 S3 的三个门现在完全一致了吗？

| 维度 | `claim` | `reserve_scope` | `lock_acquire` |
|---|---|---|---|
| 走哪个门 | `judged_role_with_nonce` | **`judged_role_with_nonce`**（本单改）| **同左**（本单改）|
| 消费 nonce | ✅ | ✅ | ✅ |
| 接受 namespace | ✅ | **✅**（本单加）| **✅**（本单加）|
| 重放判定 | `challenge_replayed` | ✅ 同 | ✅ 同 |

**⇒ 三个门在「消费 / ns / 重放」三个维度上现在完全一致。**

### 3.2 为什么不能把消费塞进 `judged_role_gated`

| 消费者 | 性质 | 若门函数消费会怎样 |
|---|---|---|
| `challenge_pending_count` | **只读**（查「还有几张票待用」）| **读一次就吃掉一张票** |
| `rsv_set` | 无 challenge 参数面 | 传 `None`，不受影响 |
| `judged_role_with_challenge`（旧路径）| 被 `judged_role_gated` 间接调 | 消费两次 |

**⇒ 门函数是「纯判定」，消费是「副作用」——把副作用塞进判定，
会让所有只读调用变成写操作。这是最基本的关注点分离。**

## 四、缺口与风险

1. **仍有一条结构性不一致**：`reserve_*` / `lock_*` 用的是**全局 `engine`（主库）**，
   加了 `namespace` 后走 `engine_for_ns`；但 `claim` 等工具一直走 `engine_for_ns`。
   现在**行为一致**了，但**两个入口并存**（全局 `engine` 简写 vs `engine_for_ns`）——
   建议后续统一（低优先，本单已让行为对齐）。
2. **`reserve_check` / `lock_status` 等只读工具现在也路由 ns**
   —— 若某个 ns 未 open，它们会 `Err` 而不是读主库。**这是有意的**
   （与 `list`/`get` 口径一致：ns 是显式的），但**存量调用方若不传 ns 仍走主库**，零回归。
3. **`s3_p2_02` 形态计数锁已随设计更新**（`judged_role_gated >= 3` → `>= 1`，
   新增 `judged_role_with_nonce >= 2`）——否则「修好了反而变红」。
4. **本单期间 `server.mbt` 被并发 lane 覆盖过一次**（脚本报 `✅` 但改动丢失，
   文件里出现 `POLLUTION-PROBE` 变异残留）。重做后立即编译+跑测试确认。
   **教训：大文件的改动要「改完立刻验证」，不能批量改完再验证。**
