## 任务 1：批量登记公钥的运维路径

### 核心矛盾（先说死）
**批量登记需要私钥，而服务端不能持有私钥。**
一旦服务端能批量生成密钥对，它就能替任何人签名 ⇒ **S3 归零**（这正是 S3 第一段就立下的红线）。

**⇒ 任何方案都只能是「服务端只收公钥，私钥永远在客户端生成」。**

### 方案对比

| 方案 | 做法 | 能覆盖 56 个吗 | 服务端持私钥 | 落地成本 |
|---|---|---|---|---|
| **① 客户端自举** | 每个调用方首次启动生成密钥对，自己走 `agent_register_key` 两步 | ✅ 新调用方全覆盖 | ❌ 不碰 | **低**（客户端改几十行）|
| **② 运维批量导入** | 管理员收集公钥清单 → 一次性导入 | ⚠️ 只覆盖**愿意配合**的 | ❌ 不碰 | **中**（需新工具 + 分发流程）|
| **③ 混合** | 新调用方自举 + 老调用方导入 + 宽限期 | ✅ 全 | ❌ 不碰 | **高**（要做两套 + 迁移期）|

### 推荐：**① 客户端自举**，理由三条

1. **唯一不碰红线的路径**：私钥在客户端生成，服务端只收公钥 —— 与现有 `agent_register_key` 完全同构，**零服务端改动**。
2. **56 个调用方里绝大多数是自动化脚本**（`cron-auto` / `execute-cron` / `atomcode-3` …），本来就该有自己的密钥文件，自举只需启动时加一步。
3. **②③ 的「批量」其实解决不了批量** —— 管理员手里没有这些脚本的私钥，只能让它们各自生成再上报，**兜一圈回到 ①**。

**① 的形态**（客户端侧，约 20 行）：`~/.fist/agent.key` 不存在就 `Ed25519PrivateKey.generate()` 落盘（0600）；
再按「已登记跳过 / 未登记走两步」处理。**服务端零改动。**

**② 保留为运维兜底**：给无法改代码的第三方，管理员手工收公钥后逐个登记（**是"代填"不是"代生成"**），预计 ≤5 个，不需专用工具。

## 任务 2：三种默认策略的对比

| | **A 维持现状** | **B 默认降权**（已部分实现）| **C 默认拒绝** |
|---|---|---|---|
| 行为 | 无钥匙 + 不传 challenge ⇒ 自报角色 | 无钥匙也降 `Executor` | 无 challenge 一律 `Err` |
| **受影响调用方** | **0** | **56**（但只降权，不失败）| **56 全部失败** |
| 恢复手段 | — | 无需恢复（降权即可用）| **不存在**（无批量登记路径）|
| 安全性 | 最低 | 中（高权操作自然被拒）| 最高 |
| 现在能切吗 | — | ✅ **能**（代码已在）| ❌ **不能**（会停摆）|

### 分步迁移路径（硬要求③）

```
第 0 步（现在）   A + 客户端自举上线，观察 2 周 → 目标 pubkey_fp 非空率 ≥80%
第 1 步（+2周）   切 B（FIST_AUTH_MODE=soft），观察 1 周：challenge_required 比例 / RANK_GATE 拒绝率
第 2 步（+3周）   若拒绝率 <5% 且无误伤 → 评估 C；前置：批量导入路径就绪（覆盖剩余 20%）
第 3 步（+4周）   切 C，必须按 ns 分批（先 scratch/测试 ns，后生产），每批观察 24h
```

## 任务 3：可回滚开关

### 设计

```moonbit
// 环境变量，读一次即缓存（不做热切，避免运行中语义漂移）
FIST_AUTH_MODE = "off" | "soft" | "strict"
```

| 值 | 行为 | 等价于 |
|---|---|---|
| `off` | 无 challenge ⇒ 自报（**默认值**）| 策略 A |
| `soft` | 无钥匙 ⇒ 降 `Executor` + `challenge_required` | 策略 B（**推荐**）|
| `strict` | 无 challenge ⇒ `Err` | 策略 C |

### 三条设计判断

1. **粒度选全局，不选 ns/agent** —— ns 级要改 schema、agent 级要改工具面，都是一周工作量，收益只是「灰度更细」。
   而灰度需求可用「**不同 server 实例设不同值**」满足 ⇒ 先全局，真需要再加。
2. **默认值首次 `off`，一周后 flip `soft`** —— `off` 等于「装了不用」，BUG-470 等于没做；
   直接 `soft` 又少一个观察窗。**两步走同时拿到「装了」和「能回滚」两个确定性。**
3. **不做热切，只读一次** —— 热切要处理「一请求跨切换点」的语义漂移（先验后不验？），
   而重启只需几秒。**用简单换正确。**

### ⚠️ 30 秒回滚操作（硬要求）

```bash
# 出问题时的完整操作（实测路径，3 条命令）
1. 停当前 server                  <kill 或 systemctl stop>
2. set FIST_AUTH_MODE=off         <Windows: setx / Linux: export + 改 service>
3. 重启                            <python scripts/fist.py serve 或 launcher>
```

**实测重启耗时**：本仓 `serve-launcher.cjs` 冷启约 **2-4 秒**（含 ESM shim 幂等重建）。
**⇒ 「改环境变量 + 重启」< 10 秒，远低于 30 秒要求。**

⚠️ **默认值必须写进启动脚本**，不能只写在文档里 ——
否则回滚时要人去「想起来该设什么」。

**做两件事，都不需额外评估：**

1. **✅ 批准「客户端自举」作为默认运维路径** —— 不碰「服务端不代签」红线，不改服务端代码。

3. **❌ 现在不批 `strict`** —— 前置不满足且缺恢复手段。若坚持，先做开关 + 批量导入兜底，再按四步走。

C 让 56 个失败且**无恢复手段** ⇒ **后悔度最大**。
