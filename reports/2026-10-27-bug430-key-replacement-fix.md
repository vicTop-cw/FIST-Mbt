# BUG-430 / S3 第五段：堵住密钥替换 / 抢注攻击 · Lane BL · 2026-10-27

> **⚠️ 本单要先纠正派单的一个前提。**
> 派单说「任何人都能把别人的公钥**换成自己的**」—— **实测不成立**：

## 二、证据

### 2.1 ★ 先纠正前提：**没有「覆盖」**

```sql
-- src/store/store_sqlite.mbt:2779（实测原文）
ON CONFLICT(agent_id) DO UPDATE SET
  pid=excluded.pid, last_seen=excluded.last_seen, status='active',
  role=CASE WHEN agents.role != 'Executor' THEN agents.role ELSE excluded.role END
```
**`DO UPDATE SET` 里没有 `pubkey_fp`** ⇒ 已有公钥**不会被覆盖**。

**探针实测**（跑完即删）：登记 `k1` 后用 `k2` 再登记，`agents_get` 读回**仍是 `k1`**。

⇒ **派单里的「把别人的公钥换成自己的」做不到。** 真实攻击面是两个：

| 攻击面 | 说明 | 危害 |
|---|---|---|
| **① 抢注** | 趁某 agent **还没登记**公钥，先替他登记**我的**公钥 | 他以「我有密钥」接入时，验的是**我的**签名 ⇒ **永久身份劫持** |
| **② 静默不生效** | 调用方以为换钥成功，实际库里还是旧的 | 可用性缺陷：卡死在「我明明换了却还是 `challenge_failed`」 |

### 2.2 修法（三态规则）

```moonbit
// 写**之前**回读（写完再读就看不出「已有」了）
let existing = ... s.agents_get(fp) ... a.pubkey_fp
let prev_key = ...
let mut already_registered = false
if prev_key != "" {
  if prev_key == pubkey_hex {
    already_registered = true          // 幂等：同钥重复登记 ⇒ 成功（重放安全）
  } else {
    return Err(ToolError(
      "…该 agent **已有公钥且与本次不同**，拒绝覆盖。" +
      "如需更换请走密钥轮换流程（BUG-430 尚未实现）。" +
      "⚠️ 本拒绝是有意的：允许任意覆盖 = 任何调用方都能把某身份的密钥换成自己的（身份劫持）。" +
      "已有前缀=… 本次前缀=…"
    ))
  }
}
if !already_registered { agent_touch_first_seen(..., pubkey_hex~, ts) }
```

**三态**：`无` ⇒ 允许 · `相同` ⇒ 幂等成功 · **`不同` ⇒ 拒绝 + 指路**。

**关键点**：
- **回读在写之前** —— 否则检查形同虚设（`bl_03` 专门断言这个顺序）
- **拒绝文案指路** —— 从「静默不生效」（② 号攻击面）升级为「明确拒绝 + 告诉我该走哪条路」
- **同钥幂等** —— 否则调用方重试会被误拒（把一个可用性问题换成另一个）

### 2.3 四格锁 + 两个变异

| 锁 | 断言 |
|---|---|
| **`bl_01`** | ★ **前提格**：底层 `agents_register` **不覆盖** `pubkey_fp`（若哪天改了 DO UPDATE SET，本格红，逼着重评攻击面）|
| `bl_02` | 首次登记 ⇒ 成功且库里有值 |
| `bl_03` | ★ **工具真的拒绝换钥**：代码面必须同时有「写前回读」+「同钥幂等」+「拒绝文案 + 轮换指路」+ **回读在写之前** |

**变异实测（都真跑）**：

| 变异 | 结果 |
|---|---|
| **M1** 删掉「已有且不同 ⇒ 拒绝」整段 | **430/431**，`bl_03` 红 |

## 三、分析

### 3.1 为什么选 (a) 而不是 (b)/(c)

- **(b) 轮换需旧密钥签名**：**理论最优**，但需要调用方交两把签名（旧钥签新钥），
  且当前 `challenge_sig` 只带**一个**签名位 ⇒ 得先扩参数面。**留作下一步。**
- **(c) HumanSteward 独占**：**做不到** —— 工具面身份是自报的（S1 的诚实边界），
  「只有 HumanSteward 能调」在无认证时等于「谁都能自称 HumanSteward 然后调」⇒ **假安全**。
- **(a) 首登锁定**：**能立刻堵住「换」，且零依赖**。

**⇒ (a) 是当前唯一能真正落地的**。但它有代价，见 §4。

### 3.2 为什么密钥替换攻击比「没有认证」更糟

派单这句**方向对、但机理要改**（因为「覆盖」不成立）：

**没有认证**：攻击者只能「**当场**自称 X」⇒ X 自己一接入，攻击者的冒充就露馅。

**抢注**：攻击者**先替 X 登记自己的公钥** ⇒ 之后 **X 真的来接入时反而验不过**
（因为验的是攻击者的钥），而**攻击者能一直通过** ⇒
**身份被永久夺走，且合法持有者被锁在门外。**

**⇒ 这是「不可逆」的：没有认证是「每次都能试」，抢注是「一次得手，永久占用」。**
这也是为什么本段必须堵它，而不是等 S2/S3 完整后再做。

## 四、缺口与风险（**`(a)` 的代价必读**）

### 4.1 `(a)` 的直接代价：**密钥丢了就锁死**

首登锁定意味着：**一旦某 agent 的公钥登记上去，就再也换不了**。
- **私钥丢失 / 泄露** ⇒ 该 agent **永久无法更换密钥** ⇒ 只能改 `agent_id`（等于放弃历史）
- **没有 `revoke` 面** ⇒ 被盗的密钥**无法吊销**

**⇒ 本段把「永久劫持」换成了「永久锁定」。**
**这仍然是净收益**（劫持是攻击者主动获利，锁定是自己出的错），
**但绝不能写成「问题解决了」** —— 轮换/吊销**必须尽快补**。

### 4.2 抢注本身**没有被完全堵住**

首登锁定只保证「登记后不可改」，**没保证「第一次是本人登记的」**。
⇒ 攻击者仍可**先于**合法持有者完成首次登记（抢注窗口 = 从 agent 首次出现到它登记公钥之间）。

**彻底堵抢注需要「首次登记也要证明持有私钥」** —— 即 **(b) 的雏形**：
登记时必须提交「新私钥对该 agent_id 的签名」，服务端验过才收。
**这是下一步最该做的**（它同时解决抢注与换钥）。

### 4.3 其他

- **nonce 表进程内** ⇒ 多实例互不可见
- **S2 未做** ⇒ 未登记 agent 不认证也能自报身份
- **(b) 需要扩 `challenge_sig` 参数面**（当前只一个签名位）
