## ⚠️ 事故记录：差点误删 dist/fist-mbt.js（已完整恢复）

**事故**：提交 memory+report 时，`git commit -F` 把暂存区里**并发 agent 预先暂存**的 `dist/fist-mbt.js` + `dist/patch_esm_main.py` 删除一并提交了（4 files / -74698 行）。
我的 `git add memory/... reports/...` 只加了我的 2 文件，但暂存区在 `git add` **之前**就已有并发 agent 的 dist 删除——`git commit` 会提交**整个暂存区**，不只是我 `git add` 的内容。

**根因**：① 提交前检查 `git diff --cached --name-only` 时看到了 dist 文件，但**没识别出那是并发 agent 预先暂存的删除**，误以为是我自己加的；② 假设了「先 git add 后 commit」只提交我 add 的内容，忽略了暂存区是**增量累积**的。

**恢复**：`git reset --soft HEAD~1`（撤销提交、保留工作树）→ `git restore --staged --worktree dist/fist-mbt.js dist/patch_esm_main.py`（从 HEAD 恢复两文件 + 取消暂存）→ 重新确认暂存区只剩我的 2 文件 → `git commit -F` 干净提交（`9a88706`）。
验证：dist/fist-mbt.js 3.3 MB 完整、dist/patch_esm_main.py 完整、dist/ 与 HEAD 一致、暂存区空、HEAD=9a88706（仅 memory+report）。

**可复用教训（最高优先级）**：
1. **`git commit -F` 会提交整个暂存区，不只自己 `git add` 的内容**——暂存区是增量累积的，并发 agent 可能已预先暂存了东西。
2. **提交前必须逐字读 `git diff --cached --name-status`**，且要判断每项是不是**自己的**。看到不认识/不该提交的文件（尤其删除 D）必须先处理（unstage）再提交。
3. **删除类操作（D 状态）绝不进暂存区**：金条四规定删除不可逆需确认。若暂存区出现非本人 `D` 条目，立即 `git restore --staged --worktree <path>` 恢复。
4. 事故后的正确恢复序：`git reset --soft HEAD~1` → `git restore --staged --worktree <被删文件>` → 清干净暂存区 → 重新确认 → 再提交。**不要 `git reset --hard`**（会丢工作树所有 WIP）。
# Round 117 · BUG-157 修复独立验证 + 单主跨进程回归判据（金条五）

**日期**：2026-10-15　**HEAD**：`9cb51bc`

## 做了什么

**只读终审并发 agent 的 BUG-157 修复**：它在 `src/store/store_sqlite.mbt` L1646-1667 的 `assistant_upsert` 加了清场 UPDATE（`UPDATE assistant_reg SET is_primary=0 WHERE is_primary=1 AND agent != ?`）+ 原有 ON CONFLICT upsert。我逐字读了完整函数体。

**关键发现——修复非原子（TOCTOU）**：清场 UPDATE 与 upsert INSERT 是**两条独立语句、无 `BEGIN IMMEDIATE` 事务包裹**。SQLite autocommit 下理论竞态：两进程都读到无人主 → 都 no-op 清场 → 都写 is_primary=1（原 BUG-157 5 进程全 elected 的变体）。

**写独立跨进程判据验证**：`scripts/blackbox/e2e_assistant_xproc.py`——用 Python `sqlite3` 逐字复刻其 SQL 形态，起 N 进程 `spawn` 在 `threading.Barrier` 同闸抢主跑多轮，任一轮 >1 行 `is_primary=1` 即 FAIL。`--atomic` 模式用 `BEGIN IMMEDIATE` 包临界区作可证明原子对照。

## 实测结果

| 形态 | 参数 | 结果 |
|---|---|---|
| 当前修复（无事务） | 5 进程 × 20 轮 | 20/20 单主成立 |
| 当前修复（无事务） | 8 进程 × 40 轮 | 40/40 单主成立 |
| 当前修复（无事务） | 8 进程 × 60 轮 | 60/60 单主成立 |
| `--atomic`（BEGIN IMMEDIATE） | 8 进程 × 40 轮 | 40/40 单主成立 |

**结论**：**BUG-157 修复实测有效但非可证明原子**。理论 TOCTOU 窗口存在，但 SQLite 文件级写串行化 + UPDATE→INSERT 紧邻使窗口实际不击穿（60/60 最高压力仍单主）。`BEGIN IMMEDIATE` 是强化项非必需。

## 可复用教训

1. **"先清场再写"两语句不等于原子**：没有 `BEGIN IMMEDIATE` 就是 TOCTOU。判据必须能造出"两进程同时读到无人主"窗口（起多进程 + Barrier 同闸），单进程（哪怕真 SQLite）结构上造不出来。
2. **SQLite 文件级写串行化可掩盖 TOCTOU**：理论上竞态，实际 8 进程 60 轮都没击穿——SQLite 对写有文件锁 + UPDATE→INSERT 紧邻。所以"实测绿"不能证明"原子"，只能说"当前负载下稳健"。
3. **诚实标注判据边界**：`e2e_assistant_xproc.py` 直测 SQL 形态，**不是**起真 `node cli.js serve` 的完整回归锁（CLI 未暴露 `assistant_claim` 子命令）。已在 scripts/README.md 与脚本 docstring 双处标注。要真回归锁需先让 CLI 暴露该命令。
