## ⚠️ 事故记录：差点误删 dist/fist-mbt.js（已完整恢复）

**事故**：提交 memory+report 时，`git commit -F` 把暂存区里**并发 agent 预先暂存**的 `dist/fist-mbt.js` + `dist/patch_esm_main.py` 删除一并提交了（4 files / -74698 行）。
我的 `git add memory/... reports/...` 只加了我的 2 文件，但暂存区在 `git add` **之前**就已有并发 agent 的 dist 删除——`git commit` 会提交**整个暂存区**，不只是我 `git add` 的内容。

**根因**：① 提交前检查 `git diff --cached --name-only` 时看到了 dist 文件，但**没识别出那是并发 agent 预先暂存的删除**，误以为是我自己加的；② 假设了「先 git add 后 commit」只提交我 add 的内容，忽略了暂存区是**增量累积**的。

**恢复**：`git reset --soft HEAD~1`（撤销提交、保留工作树）→ `git restore --staged --worktree dist/fist-mbt.js dist/patch_esm_main.py`（从 HEAD 恢复两文件 + 取消暂存）→ 重新确认暂存区只剩我的 2 文件 → `git commit -F` 干净提交（`9a88706`）。
验证：dist/fist-mbt.js 3.3 MB 完整、dist/patch_esm_main.py 完整、dist/ 与 HEAD 一致、暂存区空、HEAD=9a88706（仅 memory+report）。

**可复用教训（最高优先级）**：
1. **`git commit -F` 会提交整个暂存区，不只自己 `git add` 的内容**——暂存区是增量累积的，并发 agent 可能已预先暂存了东西。
2. **提交前必须逐字读 `git diff --cached --name-status`**，且要判断每项是不是**自己的**。看到不认识/不该提交的文件（尤其删除 D）必须先处理（unstage）再提交。
3. **删除类操作（D 状态）绝不进暂存区**：金条四规定删除不可逆需确认。若暂存区出现非本人 `D` 条目，立即 `git restore --staged --worktree <path>` 恢复。
4. 事故后的正确恢复序：`git reset --soft HEAD~1` → `git restore --staged --worktree <被删文件>` → 清干净暂存区 → 重新确认 → 再提交。**不要 `git reset --hard`**（会丢工作树所有 WIP）。
