# 调研档：反馈驱动的计划修订 plan_revise（R98 候选 · 2026-09-26）

> 来源（WebSearch 实检）：ReAct（Yao et al. 2023, arXiv 2210.03629——reasoning trace 与 action 交错，agent 依据新观测更新下一步）；CoPAL（arXiv 2310.07263, 纠正式规划——错误反馈三元组 ⟨E,R,S⟩，**可恢复中层级错误 → 局部计划修订（mid-level plan revision），不可恢复 → 高层重规划**）；OpenLegion 规划模式对比（Plan-and-Execute 的"计划在失败下变陈旧 stale under failure"正是 interleaved 修订要解决的问题）。
> 前置：R92 saga（全局补偿）、R96 saga_repair（局部补偿控级联）、R94 dag_mc（概率完工）。本档为 BACKLOG P2「Interleaved 分支：据子任务执行反馈回退改 plan，而非拆完即弃」。

## 一、核心矛盾（为什么需要计划修订）
- 现状：`task_plan_deep` 拆完即弃——计划在发布时刻生成，执行过程中的子任务失败/打回不会**回写计划本身**（哪条还成立、哪条要返工、下一步做啥）。Plan-and-Execute 模式的通病：**计划在失败下变陈旧**（OpenLegion 明确点出）。
- ReAct 的答案是"交错"：每步根据观测更新意图。fist-mbt 是编排中间层，不做 LLM 推理——所以把"据反馈修订计划"蒸馏成**可计算原语**：给定子任务执行反馈，计算计划中 keep（仍有效）/rework（需返工）/ready（下一步可做）三分。
- CoPAL 的分级纠正与 saga 家族同构：**可恢复错误 → 局部修订（只波及依赖链）**，不可恢复 → 高层重规划——与 saga_repair（局部最小补偿）vs saga_rollback（全局收尾）的二分一致。

## 二、拿来主义落地（fist-mbt 版蒸馏）
| 外部信号 | fist-mbt 落地设计 |
|---|---|
| ReAct 交错（据新观测更新计划） | 新原语 `plan_revise`：执行反馈 → 修订计划，而非拆完即弃 |
| CoPAL 分级纠正（可恢复→局部） | 修订范围 = 失败任务 + 其依赖下游闭包（cascade keep/rework 判定，复用 depends_on 反向闭包 = R96 saga_repair 同款依赖者闭包） |
| 保留承诺（Plan Commitment，R96 已用） | 未受影响子任务 keep（承诺保留），失败及下游 rework，依赖满足且未做者 ready |
| 编排中间层定位（不替代 LLM） | 纯计算：反馈由调用方给（显式 [{task_id, ok}] 或读 store 实际状态：已完成=ok，已打回/已暂停=否） |

## 三、设计要点（对照既有能力，复用避免造轮子）
- **复用**：子树收集用 `children_of` BFS（R88 progress_gate 同款）；依赖判定用 `deps_satisfied`（engine 已有）；依赖者闭包用 R96 `saga_dependents_closure` 同款逻辑；状态读取用 `list_all()`。
- **数据流**：`plan_revise(root_task_id, feedback?, ns?)` →
  1. 收集子树全部任务（children BFS）+ depends_on 边；
  2. 每任务有效态 = feedback 判定（显式 ok / 读状态：已完成→ok；已打回/已暂停/未开始→未证）+ 其全部依赖有效（cascade，环保护）；
  3. 输出 { root_task_id, keep:[已证有效且保留], rework:[无效或其依赖链受影响], ready:[依赖全部有效且未执行 = 下一步], note }。
- **零回归**：新工具独立注册（95→96），不改 plan/execute/verify 既有语义；纯读不写库（计划修订是决策建议，执行权在 agent/指挥官——与 saga 返回补偿序列同一抽象层）。

## 四、验证草案
- 单测：链 A→B→C，B 失败 → keep=[A]（A 已完成且无失败依赖）rework=[B,C]（C 级联）ready=[]；A 未做、B 完成 → keep=[] rework=[] ready=[A,B]?（依依赖：B 依赖 A，A 未做 → B 不 ready）；显式 feedback 覆盖读状态；空子树 insufficient。
- E2E：award_demo 加 R98 段（拆解→执行一条→反馈失败→plan_revise 显示 rework 与 ready）；守卫族 + cleanup CLEAN。

## 五、与机制设计家族叙事
拆解(plan_deep)→执行计划(exec_order)→**执行反馈→计划修订(plan_revise)**→排程(dag_slack/schedule/cost_route)→预算(progress_gate)→派单(executor_*)→看护(Phi)→补偿(saga_rollback/saga_repair)——"拆完即弃"变成"执行中持续修订"，Plan-and-Execute 的 stale 由 interleaved revision 修复；锚点 ReAct(2210.03629) + CoPAL(2310.07263)，纯 MoonBit 可复现（零新表，复用 depends_on 闭包）。
