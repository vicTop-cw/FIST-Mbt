## 核心原则（本机制灵魂）

> **报告不是证据，只有交付产物的实际状态才能证明工作发生了。**

fist-mbt 现有验证层已强：`run_check`（服务端真实执行命令/退出码）、`omega gate`（schema+fingerprint 语料门）、`verify`（验收闭环）、`eval_feedback`（四段式反馈）、`issue_scan`（静态高危扫描）。但缺一个：**按交付产物实际状态验证执行是否"有效"**（而非"运行过/自述完成"）。

## 设计草案：`output_validate`（产出物验证）

**五层证据梯（复用验证责任转移）**：
1. **示意层（最弱）**：agent 报告/交付字符串——默认不信，仅参考
2. **动作层**：tool 成功消息（如 run 返回 ok）——仍可假
3. **测试层**：`run_check` 退出码 0 / `moon test` 通过——比自述强
4. **产物状态层（核心增强）**：到交付产物实际机上查——文件存在？非空？期望 invariant 成立？命令产物可读？→ 新机制补这一层
5. **外部接受层（最强）**：`omega` 复验 / 验收方通过——最终门

**分层验证函数（纯+外部）**：
- 确定性硬门（先跑，快）：产物 schema/格式/必填字段/文件存在性+非空；用现有 `run_check` 执行验证命令读退出码
- 产物 invariant 门：执行者交付的产物是否满足任务完成标准（如"xxx.mbt 存在且含 YYY 符号"、`moon check` 退出 0）——用 `run_check` + 文件读
- 可选语义 judge：LLM-as-judge 评估意图对齐/领域正确（复用 `eval_feedback` 四段式通道）；低危可不跑
- **强制执行（enforce）**：verdict=fail → 触发 `report_bug(publish_task=true)` 或直接 `reject` 打回，而非仅报告

**复用清单（拿来主义）**：`run_check`（外部命令/退出码，不新造 exec）、`issue_scan`（静态门）、`omega gate`（schema/复现）、`report_bug`/`reject`（失败强制执行）、`eval_feedback`（语义 judge 通道）、`Object is Ok`/`Option`（防除零/越界）。不重复造 fork/exec/解析轮子。

**验收标准（≥5 测试）**：
- 产物缺失/空 → fail（不是靠自述）
- 新写验证命令失败（run_check 非 0）→ fail
- 产物存在且 invariant 成立 → pass
- 弱证据（仅报告字符串）缺确定性确认 → fail（体现"报告≠证据"）
- enforce=report_bug 路径：fail 写入 bugs.md 并发布修复根任务

**不越范围**：只读产物/执行验证命令，不改产物、不越权；失败即给出可读原因，交由验收方/指挥官处置。

## 现状对应

本机制与 R68-R111 已验证层互补：不替换 `verify`/`omega`，而是把「验收前按产物状态硬核预检」显式化，抬证据梯到第 4 层，落地 five-directions P1「Did it work?」。
