# 调研档：Saga 补偿事务（R92 落地 · 2026-09-26）

> 来源：Garcia-Molina & Salem 1987 SIGMOD《Sagas》（dl.acm.org/doi/10.1145/38713.38742）；工业对标 Temporal / AWS Step Functions / Cadence / DBOS；Chris Richardson《Microservices Patterns》saga 模式；Azure Architecture Center saga pattern。
> 落地：`src/engine/engine_saga.mbt` + `saga_log` 表 + 工具 `saga_register`/`saga_rollback`（91→93 工具，261→265 测试）。

## 一、模式本体（拿来主义——不重复造轮子，直接对标经典）
- **Saga 定义**：长事务拆成序列化局部事务，每个局部事务独立提交、即时释放锁；每个步骤配一个**补偿事务**（compensating transaction）。
- **失败语义**：第 N 步失败 → 对 N-1..1 按**严格倒序（LIFO）**执行补偿。
- **补偿 ≠ ROLLBACK**：原事务已提交，补偿是**新的前向事务**，做**业务逆转**（如"退款"逆转"扣款"），不是 DB 级撤销。
- **关键契约**：① 补偿幂等（retry-during-rollback 安全）；② pivot 点（之后不可补偿，需保证性设计）；③ 引擎持久化追踪待补偿栈（跨崩溃/重试/人工干预不丢）——即 BACKLOG 的 durable action log。
- **Orchestration vs Choreography**：fist-mbt 是"指挥官编排"（orchestrator），取编排式：引擎（指挥官）显式命令补偿，审计清晰、失败易推理。

## 二、为什么给 fist-mbt（"更好的 AI 项目管理工具"叙事）
- 缺口：现有生命周期（reject→retry / heal 回滚 / omega 打回）处理"任务失败"，但**多步骤任务链部分成功后的优雅收尾**没有显式原语——失败=卡死等人工清场，或整树重来。
- Saga 补上：**每个前向步骤登记可补偿动作，链失败按 LIFO 优雅收尾**——与看护族（heal/phi_accrual 判活）互补：看护发现失败 → Saga 负责收尾。
- 机制设计家族叙事闭环：拆解→排程(PERT/CPM/STAR)→预算(ZEBRA/PROGROUTER)→派单(Agora/SwarmHarness)→看护(Phi Accrual)→**补偿(Saga)**——失败不再卡死，显式补偿。

## 三、设计决策（fist-mbt 版蒸馏）
| 经典要求 | fist-mbt 落地 |
|---|---|
| 每个步骤配补偿 | `saga_register(ns, root_task_id, step, task_id, compensation, now)`——幂等：同 (ns, root, step) 重登记重置 pending 并刷新 compensation（重试安全，不位移 LIFO 位置） |
| durable action log | `saga_log` 表（append-only，id 自增，UNIQUE(ns,root,step)），`clear()` 一并清空（防测试/scratch 残留，对齐 R11/R31/R90 纪律） |
| LIFO 严格倒序 | `saga_rollback(ns, root, mark)` 只取 pending 步骤按 id 倒序返回；mark=true（默认）返回后即标 done（幂等：重复调用不再出现） |
| 补偿幂等契约 | mark=true 即消费防重复回滚；mark=false 仅预览不消费 |
| 引擎追踪 | 登记/消费全部落库，跨进程可复现（SQLite 持久化；Mem 后端 no-op，与心跳表同模式） |
| 不真正执行补偿 | fist-mbt 是编排中间层：返回补偿序列，由指挥官/agent 执行真实业务逆转动作——执行器抽象层定位一致 |
