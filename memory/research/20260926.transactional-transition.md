# 调研：Transactional transition（迁移契约检查 · Design by Contract 蒸馏）— R109

> 日期 2026-09-26 · 来源：five-directions/§一「形式化验证 | Transactional transition：invariant 失败整笔拒绝、状态 A 回稳 | Sakura Sky | engine.mbt | P2 | pending」
> 目的：给 fist-mbt 状态机迁移加"契约守卫"——任何迁移动作先过 precondition/invariant/postcondition 三件套检查，
> 任一失败**整笔拒绝**、状态 A **回稳**（不落库），实现"迁移事务化"的只读预检层。

## 一、核心锚点

### 1. Design by Contract（DbC）— Bertrand Meyer，1986 首倡 / 1988、1997《Object-Oriented Software Construction》
- 软件组件以**契约**界定行为空间：**precondition（require）**（使用前必须为真，调用方义务）/ **postcondition（ensure）**（执行后必须为真，实现方义务）/ **invariant**（整个生命周期恒真，双方共同维持）。
- 契约即"可执行规格"：错误在发生时刻被自动检测，从"后知后觉的测试"转向"结构性保证"；文档不会撒谎（执行代码即规格）。
- 继承规则：子类可弱化前置、强化后置、强化不变量（与 Liskov 替换一致）。
- 映射到 fist-mbt：**迁移方法的 precondition** = 既有 `Task::<action>()` 的 Err 语义（非法迁移拦截）；**postcondition** = 目标状态 = 文档化目标态；**invariant** = 领域恒真规则（K 值合法 / 身份保持 / assignee 纪律）。

### 2. PMAT（paiml.github.io/pmat-book/ch59）— 把 DbC 应用到 AI Agent Work Item 的直接先例（拿来主义对标）
- `pmat work` 系统实现 Meyer DbC 到**工作任务**：每个 work item 携带契约 = require（开始前，如 tests pass）/ invariant（全程，如 no new warnings）/ ensure（完成后，如 coverage ≥ 阈值）。
- 语义转换金句：**"Traditional ticket systems track what to do. Design by Contract tracks what must remain true while you do it."**
- 与本项目定位（"更好的 AI 项目管理工具"）完全同构——任务不只被"流转"，还被"契约约束"。

### 3. 事务原子性语境（Gray & Reuter 1992《Transaction Processing》概念层）
- 一组相关变更要么**整笔生效**、要么**整笔不生效**（all-or-nothing），失败不得留下半更新状态。
- 本项目为只读预检层：不真正落库，失败即"不执行"——状态 A 天然回稳（state_stable 明示）。

## 二、设计映射（Meyer 三件套 → fist-mbt 九态迁移）

| 契约件 | fist-mbt 实现 | 失败语义 |
|---|---|---|
| require / precondition | 对任务值副本执行 `Task::<action>()`（claim/split/execute/submit/reject/retry/pause/resume/reopen/complete/archive/mark_decomposing），Err 即前置失败（非法迁移原文作原因） | verdict=rejected, phase=precondition |
| invariant / throughout | 迁移后状态上校验领域不变量：IN-1 id 非空 / IN-2 depth≥1（K 值合法）/ IN-3 split_n≥1 / IN-4 身份保持（id/project_dir/ns 迁移前后一致）/ IN-5 assignee 纪律（claim/reopen 除外，其余动作 assignee 不变） | verdict=rejected, phase=invariant |
| ensure / postcondition | 目标态 == 该动作文档化目标态（claim→Claimed … archive→Archived） | verdict=rejected, phase=postcondition（理论恒真，显式声明） |

**关键演示语义**：precondition 通过 ≠ 契约通过——如 K 值非法（depth=0）任务在 Claimed 态 execute：前置（Claimed）通过但 IN-2 不变量拒绝 → **整笔拒绝、状态回稳**。这正是"Sakura Sky 蒸馏：invariant 失败整笔拒绝、状态 A 回稳"的直接落地。

## 四、风险与边界
- 纯只读预检层：不改变既有生命周期行为（零回归）；"整笔拒绝"由调用方按 verdict 执行（同 saga/circuit 的编排中间层定位）。
- invariant 均为值级规则，不读库（父/子一致性等跨任务不变量留待后续 P3 Runtime monitoring 扩展）。
- 与既有 `conflicts_check`（认领冲突预检）同族：契约检查把"预检"从认领扩到全部迁移。

## 五、结论
DbC（Meyer 1986/1997，形式化验证经典）+ PMAT ch59（MCP Agent Toolkit 的 work-item 契约直接先例，拿来主义）+ Gray & Reuter 原子性语境——三锚点支撑"迁移契约检查 tx_contract"：让"更好的 AI 项目管理工具"的任务流转带**可执行契约**，invariant 失败整笔拒绝、状态 A 回稳。纯 MoonBit 可复现（复用 Task 方法语义 + store 单任务读取，零新范式）。
