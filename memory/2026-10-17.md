## 僵尸台账清零（指挥官方案 A · 已达成）

**目标**：清空仓库根自举旧库 `fist-mbt.db`（1787 条，跨 32 ns）里 1085 条「已暂停」+ 278 条「已领取」的僵尸台账。

**关键事实**：
- `archive` 仅认 `by="human_steward"`（`by=agent/其他` 一律拒「archive 仅限人类指挥官」）；已领取态需先 `pause` 再 `archive(force=true)`。
- `archive` **不级联**：归档根任务不会带走子任务（实测 T0r482 归档后 3 个子任务仍在流）→ 必须自底向上（叶子→根）。
- `heal` 不减少僵尸数（回滚目标态仍是「已领取」），`task_cleanup` 只清已归档，二者都不构成清僵尸路径。

**执行**：1 个首跑子代理（推进 141 归档 + 66 pause，留下断点）+ 10 个分片子代理并行续跑，每片 ~123 条 id，`archive(task_id, by="human_steward", force=true)`，在流态先 `pause` 再归档。全程仅 MCP 状态机工具，**零 SQL 直写、零 `delete`、零文件改库**。

**结果**：已领取 **0**、已暂停 **0**（终态：已归档 1367 / 已完成 365 / 待领取 55）。剩余 55 条待领取属活跃流水线（tnr-polish/fist-allmodes/tnr），未误删。`done_no_artifact` 未触及（本轮只归档不验收）。子代理各自报 `failed=[]`；分片 T0r497/498/499/500 task-not-found 静默跳过。

**结论**：**archive 不级联 + 已领取需先 pause** 是本次唯一两个状态机约束；体量靠分片并行子代理消化（单子代理上下文上限 ~150 次归档调用）。

**遗留**：
- 归档≠删除：记录仍留库，`cleanup_mode=deferred`；如需物理清除走 `task_cleanup`/`delete`（不可逆，须指挥官显式授权）。
- `ops_watchdog.mbt` 仍被并发 agent 的重复 `None => ()` 分支挡（`[4139]`/`[3002]`），全仓 `moon test --target js` exit 1；归属收口仍待指挥官裁决。
