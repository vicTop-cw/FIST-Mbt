
## R70 `fix/whisperer-selftest-and-scan-gitdir`（agent-skill-docs）—— 风语者自检在 worktree 里恒红：根因不在它自己

- 上手先跑 master 上最新的 `whisperer.py --self-test`（TASK-009，别的线刚落的件）⇒ **rc=2**，
  红在 `G1 fist-gate.py --scan rc=1`。**一个工具的自检在它自己的仓库里就是红的**，这条线显然没被在
  worktree 里跑过。
- 根因（三层，逐层剥）：① `fist-gate.py --scan` 原实现用 `Path(root)/".git"/"fist"/...` 建输出目录，
  而**在 git worktree 里 `.git` 是文件**（gitdir 指针）⇒ `FileNotFoundError`；② 未捕获异常让退出码
  变成 1，于是下游把它读成"判据红了"（**异常退 1 冒充判据红**，与 BUG-303 同族的坑）；③ whisperer 的 G1
  只印 `rc=N` 不说原因，且 `run()` 不传 `cwd` ⇒ 在别的目录跑自检还会"找不到 scripts/fist-gate.py"，
  两件事叠在一起，红得没有信息量。
- 修法：`fist-gate.py` 改用 `git rev-parse --absolute-git-dir`（取不到 rc=2 拒绝"在错位置写任务"）；
  whisperer G1 固定 `cwd=ROOT`、并把结果分**三档**：绿 / **DEGRADED(rc=2) 单列** / 红带末行+提示
  （DEGRADED 既不是绿也不是"你坏了"——把它算绿会掩盖下游故障，算红会让人去翻本脚本的源码）。
- 顺带统一旗标：本工具只认 `--self-test`，而全仓惯例是 `--selftest` ⇒ 任何"对所有尺统一跑 --selftest"
  的自动化都会在它身上拿到 argparse rc=2。现两个都收（同一 dest），行为一致。
- 签收：`--self-test`/`--selftest` 均 **rc=2 → 0**；`fist-gate.py --scan` 在 worktree 里 **rc=0** 且 yaml
  落到真实 gitdir；从 `C:\` 跑 whisperer 自检仍 **rc=0**（证明 ROOT 修正真的生效，不是碰巧）。
- 方法论沉淀：**"自检红"必须先分清「我没量到」「下游坏了」「我坏了」三档**。只印一个 rc 的做法会让
  读者把三种混成一类，最后就是没人读红——本项目反复出现的那条主线。

## R74 `fix/reapply-backend-skip`（lead-2）—— reapply.sh 后端分类守卫，解 native 双臂「断且沉默」（BUG-380 方案①）

- **发现**：PR #12 CI 的 native 双臂红在 `Reapply BUG-133` 步（非编译，编译已被 #12 修）。根因：
  v0.3.10(9e0064a0) 把 native 后端从 `mizchi/sqlite` 换成 `daqing/sqlite@0.4.0`，
  `.mooncakes/mizchi/…/stub.c` **永不出现**，而 reapply.sh L53 在 TARGET 缺失时无条件 `exit 1`
  ⇒ native 臂每跑必停在这一步，把 owner 裁决③设的 `Native heap gate` 挡在门口。
- **取证**：本机 daqing 已装（`.mooncakes/daqing/sqlite/stub.c` 有 14 处 `moonbit_make_bytes`）、
  mizchi 已消失（`Test-Path .mooncakes/mizchi` = False）；`moon.pkg` 用不透明 `type Sqlite3`+`#borrow`
  ——133 那族缺陷大概率不存在，整条 reapply 链已是对旧后端的**残留补丁**。
- **修法（可逆、不删任何东西，与 fist-gate「环境态 vs 代码红」同纪律）**：加 `backend_state()`
  读 moon.mod 判 `mizchi`/`switched`/`unknown` 三态——确证已不声明 mizchi ⇒ SKIP+exit0 放行到
  heap gate 真验；仍 mizchi 却没解包 / 读不到 moon.mod ⇒ 维持硬失败（`unknown` **不猜**成"已换"，
  否则掩盖真·未解包）。`--selftest` 四格合成树驱动，S1=0 与 S2=1 的差异即分类生效的自证。
- **签收**：`bash -n` rc=0；`--selftest` **4/4 OK**；daqing worktree 三模式(apply/--force/--verify)
  全 SKIP rc=0（正是 CI Reapply 步的读数）。
- **第二层陈旧（另案入账，不在本原子改动扩范围）**：SKIP 解锁后 heap gate 探针自身仍钉
  `import mizchi/sqlite`（自含小项目 L94），测的是**旧后端** FFI 崩溃概率，不覆盖 daqing。
  改判据语义属 owner 决策，`report_bug` 入账 **BUG-381**（三档处置：改指 daqing / 撤两步退役补丁 /
  双探针过渡）。
- **教训**：① 换依赖会留下**两类**陈旧——补丁脚本钉死旧路径（本单修）与判据探针钉死旧依赖（BUG-381），
  后者被前者挡着看不见，解一层露一层；② "断且沉默"比"红着"更危险——native 覆盖停了两天没有一条
  红话解释，只因 reapply 的 rc=1 长得像"环境问题"；③ CI 基础设施的删除/退役（撤 reapply 步、撤 heap
  gate）是金条四 owner 面，我用分类守卫先把"沉默"变"有读数的 SKIP"，退役决策留给拍板者，不替 owner 拆门。
